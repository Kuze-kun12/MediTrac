
Final Project: Plain-Language Guide 
Courses: Database Management Systems 1 (DBMS 1) and Systems Integration and Architecture (SIA) 
This is a simplified rewrite of the official final project.md . It does not replace the official guidelines. If the two ever disagree, the original wins. 
Section 11 records the rulings on the points the official text left open. Items marked (suggested) are recommendations, not requirements: the suggested split, the weekly commit check, the defense timing, the suggested timeline, and the repository checklist. 
1. The Big Picture 
You build a software system with your group of 3 to 6 members. 
You get graded mostly as an individual (90%) and a little as a group (10%). 
Your Git history proves what you personally did. If you didn't commit it, it doesn't count. Every line you submit must be your own work, and you must be able to explain it at the defense. 
2. Picking Your System 
Stick to your approved title 
Build what your instructor approved. 
Want to change the topic or scope? Get written re-approval first. 
Don't build a generic system 
Plain CRUD apps (basic POS, basic online store, basic inventory, basic clinic log) won't get full credit. If your topic is a common one, you need at least one major feature that is specific to your domain.

E-commerce: escrow or milestone-based payments, tiered pricing by volume or customer type, or automatic dispute escalation.

Quick test: is your feature a major one? You should be able to answer "yes" to all four. 
1. Does it apply business rules or calculations, instead of only storing and showing data? 2. Does the system do something on its own (an automatic check, alert, calculation, or status change)? 3. Can you demo it with sample data, a clear expected result, and one tricky edge case? 4. If you removed it, would the system look like any generic CRUD app?

Independent Track: the two projects can have different rosters. Apply this section separately to each project.

Join reports: report screens or endpoints that run a join. Across the group, INNER , LEFT/RIGHT , and FULL OUTER must each appear at least once. In the Merged Track, write the join in the Model and expose it as a GET report endpoint. One piece of code then serves both courses. 
Complete resources: an entity with working GET , POST , PUT/PATCH , and DELETE through Model, Controller, and Route, used by the frontend. (DBMS 1-only teams: a full form or screen with create, read, update, and delete.) 
Real tables only: each table must be a real entity with real relationships. Padding the schema to hit the number won't survive the question "why does this table exist?" 
At any group size, every member owns at least: 
2 tables 
1 complete resource 
1 join report 
1 frontend screen that uses their own endpoints 
5.2 Own a slice, not a layer 
Split the work by feature area, not by layer. If one person writes all the Models and another builds all the screens, the screen builder can't explain SQL joins or MVC at the defense, and the Model writer can't show anything working. 
Each member takes a feature area end to end: tables, Model, Controller, Route, a frontend screen, and a join report. 
The group chooses who covers which MVC layers and which join types. The instructor does not assign them. Decide it inside your slices, make sure all three join types are covered, and record the choice in the ownership matrix (5.4). 
Everyone writes code. A member who only does documentation, testing, or slides leaves no authored modules to defend, and the individual grade is built on authored code.

6. Git Rules (This Decides Your Grade) 
Repository on GitHub, public or accessible to the instructor. 
Your Git history is the main evidence for your 90% individual grade. 
Do 
Commit from your own GitHub account 
Commit often, in small steps, throughout the project 
Write meaningful messages ( feat: add batch expiry check , not update ) 
Use feature branches and pull requests 
Avoid (severe deductions) 
One big upload near the deadline 
All commits coming from one person 
Commits made by someone else on your behalf 
Inactive members 
A member who is inactive receives an automatic score of 0. Your Git history is the evidence, so use the weekly commit check below to catch problems early. 
What is not counted 
These do not count toward your Git contribution: 
Squash-merged pull requests 
Co-authored-by credit for pair-programmed work 
Commits made by editing files in the GitHub web editor 
Team workflow 
Protect main . Nobody pushes straight to it; everything goes through a pull request. Rotate reviewers. Someone other than the author reviews each PR, ideally a different person each time. 
Name branches by owner and purpose, such as feature/ana-batch-expiry . 
Use semantic commit prefixes: feat: , fix: , refactor: , docs: . 
Check your Git identity. Run git config user.email and make sure it's an email linked to your own GitHub account. Otherwise your commits may not show up as yours. On a lab PC or borrowed laptop, check it before every session. 
Commit from your own machine, not the GitHub web editor. Write your code in a local clone, commit there, and push. 
Pair programming is fine, but take turns committing. Co-authored-by lines are not counted, so each person needs commits of their own. 
Merge with a regular merge commit, never a squash. Squashing turns a branch of small commits into one commit on main , and squash-merged PRs are not counted. Choose "Create a merge commit" when you merge a PR.

Don't force-push shared branches. It breaks teammates' work and can erase commit evidence. The instructor takes a snapshot of your repository at the deadline. You don't need to create a tag or a release. Push and merge everything you want graded into main before the deadline. 
Weekly commit check (suggested) 
Once a week, on an up-to-date main , run git shortlog -sne --no-merges HEAD . It lists commits per author. An even share is 100% divided by the number of members, and anyone under half of that is a red flag worth fixing early.

Individual points vs. group points 
Individual points (90) are yours alone. They don't move because a teammate did better or worse. Group points (10) are shared, so everyone in the group starts from the same group score. The exception is an inactive member, who receives an automatic score of 0 (Section 6). Group size doesn't change the point values. That is why Section 5 sets a minimum footprint per member: it keeps the 90 individual points equally reachable in a team of 3 and a team of 6.

8. Defense Day (Time and Format by Group Size) 
Suggested time per group 
The group demo covers the 10% group portion. Then each member has their own short defense: about 5 minutes walking through their own code and about 5 minutes of questions. In the Merged Track, this one defense is graded for both courses.

What to expect 
A random file or line is picked and the question is "who wrote this?" (expect git blame ). You explain it line by line, including why it was written that way. 
You're asked to make a small live change: add a field, change a join, return a different status code. You may be asked how your slice connects to a teammate's. 
Demo script for the group portion 
1. Log in and show the main flow (Transactions). 
2. Run the unique feature, including one tricky edge case. 
3. Show the join reports ( INNER , LEFT/RIGHT , FULL OUTER ). 
4. Show the API behind one screen, using the browser's network tab or Postman. 
5. Close with the ER diagram and the MVC structure in about a minute. 
Let each member drive the part that belongs to their slice, so the whole group speaks. Seed realistic data and do a full dry run before the day, and keep a plan B (local copy, screenshots) in case the network or database fails.
